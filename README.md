# RunesIOS

Native iPhone client for Meta Neural Band connection, verified enrollment, built-in gesture reception, and background sessions. Requires **iOS 26 or later** and full **Xcode 26 or later with an iOS SDK supporting the connected phone**. The checked-in Xcode project opens directly; Python and project-generation tools are not required to build or run it.

This is the first implementation of the product's native connection and gesture pipeline. Hardware behavior, Meta sign-in, and screen-off delivery have **not yet been verified on an iPhone**. Background support is implemented using Core Bluetooth and a user-started Live Activity; it is not a promise of indefinite execution.

## Open and install

1. Install full Xcode and its iOS platform support. Command Line Tools alone cannot build this app. Launch Xcode once to finish installation. If needed select it with `sudo xcode-select --switch /Applications/Xcode.app/Contents/Developer`.
2. Open `RunesIOS.xcodeproj` and choose the **RunesIOS** scheme.
3. In Xcode Settings → Accounts, sign in to your Apple Account. Select your team in **Signing & Capabilities for both RunesIOS and RunesActivity**. If these bundle identifiers are unavailable, change the app identifier and give the extension the same prefix plus `.activity`.
4. Connect your iPhone, trust the Mac, and enable **Settings → Privacy & Security → Developer Mode** if prompted. Select the phone as the run destination and press Run. No App Store submission is required for local development.
5. A free Personal Team can be used for local development where supported; its short provisioning lifetime requires periodically rebuilding. Xcode will report any account/capability limitations.

The Simulator can run the interface but is not evidence of Bluetooth, pairing, or screen-off operation. This project deliberately has no simulated band or test-only runtime paths.

## Using the app

On first launch Runes walks through setup: welcome → allow Bluetooth → pairing mode → choose your band → Meta sign-in (with a plain warning that the band may disconnect from other devices such as the Mac) → a "tap your index finger" check → done. A band that already has a saved setup on this phone skips sign-in. **Use my Mac’s setup instead** imports the Mac identity by QR (see below) rather than signing in.

After setup the main screen is a single ring that shows **Not set up, Connecting, Connected or Needs attention**, and it ripples when a gesture arrives. Battery, wrist and last gesture sit under it, and the Mac link (`SessionController.relayStatus`) appears as one line at the bottom. Problems appear as one sentence and one button. Protocol detail never appears on screen; it goes to the journal. Settings has forget band, haptics, battery alerts, privacy and licenses. **Settings → Motion lab** (`Workouts/MotionLab.swift`, `Workouts/MotionRecorder.swift`, `Views/MotionLabView.swift`) records labelled sets of any exercise with every raw band stream — gyroscope, orientation, gestures and 8-channel 2048 Hz EMG (`Protocol/EMG.swift`; requested only while a set records, and a refusal turns EMG off instead of dropping the link) — runs the shipping rep detector alongside, and exports all sets as one zip with a README of the formats. Checks: `Tests/MotionLabTests.swift`. **Settings → Advanced** holds journal export, Mac test receiver pairing, Mac identity import and raw packets.

The look follows the Mac app (`docs/design.md`) and is written up in `Documentation/StyleGuide.md`: monochrome, Geist (bundled under the OFL in `Resources/Fonts`), 6 px controls, 8 px panels, 200 ms motion, plus a matching dark mode. Tokens and shared parts live in `Views/Design/Theme.swift`; `RUNES_SNAPSHOT=style-guide` shows the guide as a screen. Reduce Motion and Dynamic Type are respected. SwiftUI previews in `Views/Previews.swift` use fixed view states. In DEBUG builds, `RUNES_SNAPSHOT=<name>` shows one of those states for screenshots without starting the session. There is still no simulated band.

## Mappings

The hand button on the home screen opens **Mappings**, the iPhone version of the Mac app's Motions page: profiles, one row per gesture, combos (2–8 steps, hold/release pairing, the Mac's timing choices; steps can be recorded from the band), and one action or several linked actions run in order. Every gesture in the app is set the same way, with the trigger composer (`Views/Design/TriggerComposer.swift`, rules in `Mappings/TriggerRules.swift`): a track of the steps, with a line under the ones made while a finger is held, and a pad of every gesture laid out by finger, swipe and wrist. Touching a step selects it, and the pad then changes it, or it can be moved or removed; touching the dashed slot adds after it. **Make it on your band** listens instead: the next gesture, or run of steps, is taken from the band, and while it listens the band's gestures reach the editor and nothing else (`MappingStore.paused`). A key lights when the band makes its gesture. A combo's editor shows the track and opens the pad when a step is touched; Score, Capture, Workouts and Cook open the same composer as a sheet (`TriggerSheet`), each taking one gesture or a combo: finger and swipe steps in Score and Capture, and rotation, movement and air steps too in Workouts and Cook. A running workout or recipe takes the motion its combos use, so mappings with the same kind of step are off meanwhile. `Mappings/MappingEngine.swift` is a port of the Mac's `ShortcutEngine` combo logic. Actions are iPhone-native (Apple Shortcut, open link, web API, notification, copy, haptic, wait, profile switching). API calls, notifications and profile switches also run while the phone is locked; opening apps, copying and haptics need Runes on screen. Combos can also use **rotation** (axis, and left/right/either way) and **movement** (axis) steps, detected with the Mac's thresholds (25° rotation, gyroscope above 80 re-arming below 30). The phone asks the band for orientation and gyroscope only while a live combo uses them; the Mac relay still receives only the streams the Mac requested. Combos can also use **air gesture** steps (`Mappings/AirGesture.swift`, `Views/AirGestureEditor.swift`): a shape drawn with a finger or recorded with the band, matched with the Mac's DTW matcher after the preceding gesture, within the step's own 0.5–10 s window; competing shapes go to the highest similarity above its minimum. They're saved in the Mac's format. Icons are the Mac's: Lucide 0.468.0 path data in `Views/Design/LucideData.swift` (generated by `Tools/lucide-icons.js`) and the Mac's hand-drawn finger icons in `Views/Design/Icons.swift`.

## Applications: Workouts

The grid button on the home screen opens **Applications**. The first app is **Workouts** (`Workouts/`, `Views/WorkoutsView.swift`, `Views/WorkoutTabs.swift`, `Views/BodyMap.swift`). It has three tabs. **Today** shows a hairline body, front and back: each muscle fills with ink when a set trains it and fades by a seventh each day after, back to an outline after a week (muscles a set only works second-hand count half). Below it are Start workout, which asks which day of your split to do and suggests the one after your last, and this week's reps. **Split** holds your training days (a push/pull/legs starter on first launch); each day lists exercises with sets, target reps (seconds for timed ones) and an optional weight. **Journal** shows workouts this month, sets this week, a weekly streak, sets per week, sets per muscle over the last 7 days, each exercise's best and a per-session sparkline, and every session. The exercise picker (`Workouts/ExerciseCatalog.swift`, 112 exercises, most popular first) filters by group, searches by name, equipment or muscle, and marks the 28 exercises whose reps the band can count with a waveform. Reps come from the band's orientation (forearm swing away from where the set started) or gyroscope bursts. Exercises the band can't follow log their target reps when the set stops; timed ones log the time between start and stop. The gear on Workouts opens its settings: the four global gestures (start set, default double tap index; stop set, double tap middle; repeat last set, swipe left; skip set, swipe right), each of which can instead be a combo of two to eight steps, rotation, movement and air shapes included (`CommandTrigger`, decided by a `MappingEngine` through `TriggerDecider`, as in Score); while a workout runs every mapping that uses one of those gestures is off (`WorkoutControls.reserved`), Low/Normal/High rep sensitivity (thresholds are untuned guesses), kg or lb, and clearing the journal. The Live Activity shows the current exercise, the live count (throttled to 1 update/s), the last logged set and the next one, and it alerts with a sound when a set is logged. Checks: `Tests/WorkoutTests.swift` (see its header for the `swiftc` line).

The second app is **Score** (`Scores/`, `Views/ScoreView.swift`): two to six players (named Player 1, Player 2 and so on until renamed), each a block of colour with one number (the one screen in Runes that uses colour; `ScoreTint` in `Shared/`). It is full screen, one player at a time: tap to add a point, the bar in the corner to take one away, the name to rename or remove that player. Swipe up to zoom out to everyone at once, where the game is started, reset and given more players (it opens there until a game is live); swipe down zooms back into the selected player. One at a time the players sit side by side in order like pages: swipe left for the next player and right for the one before, and they slide past. In the grid, swiping right moves the outline to the next player and left to the one before. The screen follows whoever was changed last, the phone stays awake while it is open, and it is the only screen that turns to landscape (`OrientationLock` in `RunesIOSApp.swift`). **Start game** gives the band its gestures until **End game**. Which gesture does what is chosen in **Score settings** (the gear in the everyone view; `Views/ScoreSettingsView.swift`, `ScoreControls`): add a point to or take one from the selected player (default double tap and tap-and-hold index), next and previous player (swipe right and left), and optionally a point to or from a particular player. Each action takes one gesture or a combo of two to eight finger and swipe steps with the Mappings timing choices; motion and air steps are left out so the motion sensors stay off during a game. No two actions share a trigger (choosing one another action has swaps them), and swipe up stays with the screen's zoom. A dedicated `MappingEngine` decides which trigger fired, so combos and double-tap waits behave exactly as in Mappings. While a game is live every mapping that uses one of the game's gestures is off (`ScoreControls.reserved`: each trigger's gestures, plus a finger's tap with its double tap and its release with its hold), including combos with such a step; Mappings shows them as "Off during the game" and they come back when it ends. Every change made from the band is confirmed by the Live Activity, which alerts with a sound and the new score; the Lock Screen and Dynamic Island show the numbers. Nothing is spoken. While a game is live the phone also plays sounds so it can be kept by ear with the phone locked (`Scores/ScoreAudio.swift`): one for a point added, one for a point taken away, and one per player when they are selected. The point sounds (Resolve and Bounce by default) are chosen in Score settings from the Mac app's whole library of 32 voices (`Sounds/SoundLibrary.swift`, a sample-for-sample port of `src/connectBell.ts` rendered offline), with a volume and an off switch. Player sounds are picked as one of five curated sets (`ScorePlayerSounds`: Mallets, Chimes, Arcade, Percussion, Soft), so every player always has a different voice, plus their own pitch. Any of them can be None. It runs a silent audio loop under the `audio` background mode for as long as the game is live, mixed with any music and audible with the silent switch on. A paired Mac still receives the raw gestures. Checks: `Tests/ScoreTests.swift`.

The third app is **Cook** (`Cook/`, `Views/CookView.swift`, `Views/CookingView.swift`): recipes read one step at a time, turned and timed from the band, so wet or floury hands never touch the phone. A recipe is added by pasting its text or a link. Text is sorted into a title, ingredients and steps by `RecipeParser` (headings when there are any, the shape of each line when there aren't); a link is fetched and the schema.org Recipe data most recipe sites publish is read from the page (a site that turns the request away, or has none, says so and asks for the text). Every time a step mentions ("simmer for 15 minutes", "25–30 min", "1 hour 30 minutes", "an hour and a half") becomes a timer named after the step's verb (`DurationFinder`; a range runs to its lower end). The editor is one page of text that says underneath what Runes makes of it. The cooking screen shows the step in large type over the step's timers, all of them at once, as large numbers and nothing else: muted while waiting or paused, ink while counting, and on ink when the time is up, until it is stopped. On a step that mentions two or more times, the selected timer has an outline and its time is bold in the text; the band's swipe down and up move the selection (`CookSession.slot`) and its other gestures act on the selected timer. There are no buttons. Steps are pages: swipe sideways on the band or the screen, and swiping on from the last step finishes the recipe. By touch, tap a number to start or pause it (which also selects it), hold it to reset it, and swipe up on it for another minute; none of that is written on screen, since the band is the main way in. What the band's gestures do right now is listed along the bottom (next, start or pause, +1, reset, timer). Timers from other steps wait on a shelf above that row as a step number and its time, and the phone stays awake.

Three things in `Views/CookingView.swift` keep the page still while parts of it change, and each is there because the simpler version visibly misbehaved. The bold moves between times without any other word moving: bold letters are wider, so each bold word is tracked tighter by exactly its extra width (`StepPage.widening`), and the step is drawn as layers (the words without their times, then each time plain and bold) so that only one time's weight fades, in place. SwiftUI's own text transition made the time vanish and slide back in. The words are drawn without a scroll view whenever they fit (`ViewThatFits`). And each number, and the layered text, is its own `geometryGroup`: a counting number animates its digits every second, and without the group that animation was also applied to where the number is, so it trailed behind the text when the page slid.

Defaults, changed in Cook settings: swipe right for the next step and left for the one before; double tap index to start, pause and restart the selected timer (or stop one that is ringing); double tap middle for another minute; tap and hold middle to reset it; swipe down and up for the next and previous timer of the step. Each command takes one gesture or a combo of two to eight steps, rotation, movement and air shapes included, which keep the band's motion sensors on only while a recipe is being cooked (`CommandTrigger`; a `TriggerDecider` decides which was made, so a gesture that also starts a combo waits for it). While a recipe is being cooked those gestures are Cook's and mappings that use them are off. Timers are absolute end times saved with the session, so they survive the phone locking and Runes being closed: each also schedules a notification. The Live Activity shows only the step number and the timers: one timer as its time, counting by itself, and two or more as circles that fill as they run out (a dimmed ring while paused, a solid disc once the time is up). A starter recipe is there on first launch. Checks: `Tests/CookTests.swift`.

The fourth app is **Capture** (`Capture/`, `Views/CaptureView.swift`): make a gesture, say the thought, and it is written down. The gesture is chosen in Capture settings (`CaptureTrigger`): any single gesture, or a combo of two to eight finger and swipe steps with the Mappings timing choices (`TriggerSheet`, shared with every app). It starts a recording and, made again, saves it. When it ends with a finger held (a hold on its own, which is the default, or a combo whose last step is a hold) the note records for as long as the hold and saves when that finger lets go. A dedicated `MappingEngine` decides when the trigger was made, so combos and double-tap waits behave as in Mappings. While Capture is on screen or pocket mode is on, the trigger's gestures are Capture's and mappings that use them are off. Each note keeps its recording (AAC, in Application Support/Capture) and, once transcribed, its words; notes are listed by day and open to edit, play, copy, share or delete. Transcription is on the phone (`CaptureTranscriber`: `SpeechTranscriber`, falling back to `DictationTranscriber`, with the audio converted to the model's own format); nothing is sent anywhere. With Capture on screen the band's trigger opens the microphone when it arrives; holding the circle does the same, and a tap on it records until the next tap. **Pocket mode** is for a locked phone. iOS refuses to *start* a recording from the background but lets one that began in the foreground continue, so pocket mode opens the microphone while Runes is on screen and leaves it open: sound is discarded as it arrives, all but the last second, until the trigger says to keep it (that second goes in first, so the word spoken while the gesture was being recognised isn't cut). Its switch is the first thing in Capture settings. The orange microphone indicator is therefore on for as long as pocket mode is, and a line at the top of Capture says so. Pocket mode leaves the Live Activity alone: the cues are the sign that a note started or was saved. Capture settings choose them (`CaptureFeedback`): **Sounds**; **Buzz**, where the phone vibrates once to start, twice when saved and three times when too short to keep (`AudioHub` allows vibration while recording), and away from Runes one replacing notification says the same; or **Off**. If a call or another app takes the microphone, iOS won't give it back in the background; a notification says to open Runes. Capture settings choose pocket mode, the gesture, the microphone (the iPhone's, which leaves headphone music at full quality, or the headphones', which drops wireless ones to call quality while it is on) and the cues. A recording shorter than 0.6 s is discarded, and one that is never ended stops at five minutes. Mappings also has a **Record a Capture note** action (`MappingAction.capture`, `CaptureStore.toggle`): give it to any gesture or combo and it starts a note from any screen, and saves it when made again, or on the release when the gesture ends with a hold (`Mapping.endingRelease`). Unlike Capture's own trigger it reserves nothing. With Runes in the background it needs pocket mode; without it, a notification says so. Capture's cues play through the recorder's own engine: a second engine starting beside it reconfigures the hardware and would end the recording it announces. Checks: `Tests/CaptureTests.swift` for the values and the trigger rules (start, again to save, release to save after a hold, combos); the transcriber was checked natively on the Mac against a synthesized clip, and it does not run in the Simulator (its speech models offer no audio format there).

**Switch controls** (`Mappings/SwitchControls.swift`, `Session/ControlSwitch.swift`, `Views/Design/ControlsCover.swift`): one combo of two to eight finger and swipe steps that, while Workouts, Score or Cook runs, hands the band to the regular mappings and back. It is saved beside the profiles (`MappingLibrary.switchControls`), so it is the same in every profile, and it is set from Mappings or any of the three apps' settings (one setting, one sheet). An app always starts with its own controls. With the regular controls selected the app keeps running (reps count, timers run, the score stays) but takes no gestures, so every mapping is live. Whoever has the band holds the combo in its own `MappingEngine` (the first running app, or `MappingStore`), so a gesture that begins it waits for it and its steps run nothing else; a trigger made of exactly the same steps gives way, and the composer refuses to save one. With the app's controls selected nothing is added: its screen and the Live Activity are as they always were. With the regular controls selected the app's screen blurs behind the Runes mark (touching it hands the band back), and the Live Activity shows the band status instead of the app, as with no app running. Switching plays two notes, rising into the app and falling out of it; with the phone locked the Live Activity alerts as well, since a sound can't always be started from the background. Capture is not part of it, and a paired Mac still receives the raw gestures. Checks: `Tests/SwitchControlsTests.swift`.

**Home Screen widgets** (`RunesActivity/AppWidgets.swift`, in the same extension as the Live Activity): **Runes app**, a small widget that opens one app, and **Runes apps**, a medium one with up to four, each chosen by touching and holding the widget (`OneAppIntent`, `FourAppsIntent`; empty slots and repeats are dropped). A tap opens `runes://app/<id>` (`Shared/AppLink.swift`, scheme registered in `Info.plist`). The link arrives through `LinkSceneDelegate` in `RunesIOSApp.swift` rather than only `onOpenURL`, because SwiftUI hands `onOpenURL` to the frontmost presentation and `RootView` never saw links while an app was open. `RootView` then swaps the open app in place, or waits for Settings, Mappings or Applications to finish closing before showing it. Before setup is finished a link only opens Runes.

Everything that plays or records goes through one audio session (`Sounds/AudioHub.swift`): Score's cues, Cook's bell and Capture's microphone ask for it by name, and it is switched off only when nobody holds it.

## Staying connected

- **Never gives up on ordinary errors.** Only an identity or ownership rejection (or OS pairing mismatch) turns auto-connect off, and so does the person pressing Disconnect. Transport, protocol and locked-Keychain errors back off 1, 2, 4, 8, 16, then 20 s indefinitely; each wait holds a background task so the timer can fire.
- **Pending connects, not timers.** When the link drops, the transport immediately leaves `CBCentralManager.connect()` pending, with `CBConnectPeripheralOptionEnableAutoReconnect`. A pending connect has no deadline, so the band reconnects whenever it returns, even while the app is suspended. Only setup steps after the link is up have a 60 s deadline. Background scans look for the advertised `FD5F` service, not `FEB8`.
- **Band pulse.** The subscription to `2D41DA7A`/`2D41DA7C` (see `Documentation/WakeTest.md`) is kept. If it stops for 30 s, the app shows a gentle "Gestures may pause while your phone is locked" with **Reconnect**.
- **Battery** comes from the standard battery service (`180F/2A19`, read + notify). **Hand** comes from the same `read_hand` RPC the Mac app uses; if the band rejects it twice, it is never asked again.
- **Gesture sequences.** The band numbers raw gestures and derived interactions with two separate counters. The journal now tracks each one separately. In the 2026-11-08 export, 2,368 "discontinuity" rows came from comparing the two counters; split per stream, 0 of 3,076 gestures were discontinuous.
- **Live Activity** is minimal (state only) and has no expiry reminder. It does not affect background execution and could be dropped.

### Band picker (AccessorySetupKit)

`Transport/AccessoryPicker.swift` implements the system picker but is **off by default**. Turn it on by adding `NSAccessorySetupKitSupports = [Bluetooth]` and `NSAccessorySetupBluetoothServices = [FD5F]` to Info.plist. Trade-off: on iOS 26 only AccessorySetupKit apps are relaunched after a force quit, but in that mode Core Bluetooth can only reach accessories chosen in the picker. That would likely break the Core Bluetooth link to the Mac (`Relay/`). Without the keys, onboarding uses the in-app scan.

## Import the Mac identity by QR

On the Mac, disconnect the band, then run `swift Tools/ShowMacIdentity.swift <Mac-device-ID>`. On iPhone, choose your band and pick **Use my Mac’s setup instead** (onboarding) or **Settings → Advanced → Use my Mac’s band setup**. The QR **contains the private authentication key**, so keep it out of screenshots. The imported identity replaces the saved one only after it authenticates.

## Journal

**Settings → Advanced → Export journal.** The journal is two rotating 2 MiB segments, excluded from backup and free of tokens and private keys. It records gestures, connection transitions, lifecycle, sanitized errors, battery, hand, pulse and per-stream sequence discontinuities.

## Command-line builds

With full Xcode installed, simulator compilation requires no team:

```sh
xcodebuild -project RunesIOS.xcodeproj -scheme RunesIOS -configuration Debug -sdk iphonesimulator -destination 'generic/platform=iOS Simulator' CODE_SIGNING_ALLOWED=NO build
```

For an unsigned device compilation:

```sh
xcodebuild -project RunesIOS.xcodeproj -scheme RunesIOS -configuration Release -sdk iphoneos -destination 'generic/platform=iOS' CODE_SIGNING_ALLOWED=NO build
```

To install a standalone signed build, select your phone, edit the scheme's **Run → Info → Build Configuration** to **Release**, uncheck **Debug executable**, then Run. Stop the Xcode session and launch Runes from the phone's Home Screen. It does not use a Mac development server. Keep the same bundle ID and signing team between rebuilds to preserve the phone's Keychain identity.

## Structure and provenance

- `RunesIOS/Protocol`: bounded protobuf/DataX decoding, AirShield records, mutual trust, RPC and gesture subscription.
- `RunesIOS/Transport`: Core Bluetooth and L2CAP stream I/O on the session run loop.
- `RunesIOS/Authentication`: Meta service exchange, isolated login, persisted ownership ceremony.
- `RunesIOS/Session`: connection lifecycle, observable UI adapter, typed gestures, and Live Activity management.
- `RunesIOS/Persistence`: protected Keychain identity storage and rotating local journal.
- `RunesIOS/Views`: connection, gestures, packet details, and diagnostics.
- `Shared` / `RunesActivity`: ActivityKit attributes and Lock Screen/Dynamic Island presentation.

Protocol reference: the installed **meta-neural-py 0.1.0a1** source, captured as SHA-256 entries in `Documentation/ProtocolReference.sha256`. The Swift implementation is a port of the required paths, not an official Meta mobile SDK. Third-party attribution is in `THIRD_PARTY_NOTICES.md`. No neighboring repository is needed at runtime or build time.

`generate_project.py` can regenerate the checked-in project using Python's standard library if source membership changes; it is optional and never runs during a build. Signing-team selection is kept in Xcode. No development team or account credentials are committed.
